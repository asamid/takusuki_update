# v4.1.0 Production performance validation

Observed: 2026-10-25 01:52–07:54 JST. Target: Production `192.168.100.29`.

This was a read-only, low-load observation. It did not run `EXPLAIN ANALYZE`, a load benchmark,
database maintenance, a statistics reset, a setting change, a service operation, or a patch
operation. Five public search requests were sequential. The deployment result and 21-second
application-level outage are operator-provided facts; systemd independently recorded a stop at
01:52:16 and a start at 01:52:33.

## Decision

Patch 030 has removed the blocked-host SQL parameter explosion in Production. A representative
pre-update timed-out PGroonga statement was 167,351 characters with highest bind `$20857`. Of 277
post-update timed-out PGroonga statements inspected, 276 were 12,820–12,821 characters with highest
bind `$3`; one query variant was 16,514 characters with highest bind `$7`. All 277 used the new
`generate_subscripts` suffix path and none used the legacy expanded array. The blocked-host portion
itself is 20,826 spread binds before 030 and two reusable array binds after 030.

This is a confirmed structural improvement, but search latency is not fixed. Misskey recorded 271
`notes/search` timeout events from startup through 07:45:58 JST, while PostgreSQL recorded 277
optimized PGroonga statements reaching the timeout in the same period. The equivalent initial
522-second service windows contained 10 search timeout events before the update and two after it,
but total search request counts were not readable. Therefore no Production timeout reduction
percentage or latency improvement percentage is claimed.

## Search SQL structure and execution

The representative statements below are real Production timeout statements and contain the
PGroonga `&@~` operator. Character count includes the log's statement prefix, so it is useful as a
same-collector trend rather than an exact wire byte count.

| Representative statement | Pre-update | Post-update |
| --- | ---: | ---: |
| observed at | 01:47:18 JST | 01:58:18 and 01:58:28 JST |
| logged characters | 167,351 | 12,820 |
| highest positional bind | `$20857` | `$3` |
| bind occurrences in statement | 20,857 | 7 |
| blocked-host implementation | expanded `NOT ILIKE ALL(ARRAY[...])` | suffix equality plus wildcard array |
| blocked-host bind values | 20,826 | 2 reusable arrays |
| outcome | statement timeout | statement timeout |

The logged text reduction is 92.34% and the highest bind position reduction is 99.99% for these
representative statements. Those are SQL-shape reductions. They must not be read as execution-time
reductions because both examples timed out and their non-block query options may differ.

The extended post-update statement-shape population was:

| ---: | ---: | ---: | ---: | --- | --- |

| 1 | 16,514 | `$7` | 30 | yes | no |

All 277 therefore prove that the deployed path kept the two reusable blocked-host arrays under
real traffic. Their timeout outcome also proves that parameters were not the only remaining cost.

## Timeout and worker windows

The comparison uses two equal 522-second service-active windows: 01:43:34–01:52:16 and
01:52:33–02:01:15 JST.

| Signal | Pre-update | Post-update | Interpretation |
| --- | ---: | ---: | --- |

| PGroonga statement log lines | 50 | 2 | parallel error logging multiplies pre-update statement lines |
| `parallel worker` log lines | 88 | 0 | line occurrences, not a count of distinct workers |
| all Misskey journal lines | 28,419 | 29,221 | overall log volume was similar, but it is not a search-access denominator |

Ten one-second process snapshots after the API probes observed zero PostgreSQL parallel workers.
The configured limits remain `max_parallel_workers=24` and
`max_parallel_workers_per_gather=4`; no setting was changed. The absence of workers in the short
post-update sample and timeout logs is favorable, but it does not prove that no parallel worker
will be used under future plans or peak traffic.

The longer 01:52:33–07:45:58 post-update interval contained 271 Misskey search-timeout events, 277
PostgreSQL timeout errors, 277 PGroonga statements, and zero `parallel worker` log lines. Hourly
Misskey event counts were 2 in the partial 01:00 hour, then 31, 60, 29, 38, 60 and 51 through the
partial 07:00 hour. These counts demonstrate persistence, but without the number and mix of all
search requests they are not a timeout rate.

## CPU and database state

At 01:56–01:58 JST, load average was 1.35/1.66/1.21 on 24 vCPUs. Four `vmstat` samples showed
97–99% idle CPU, zero iowait, zero steal, and no swap input/output. CPU PSI was 0.06 at 10 and
60 seconds; memory PSI was zero. During a five-second `pidstat` observation, PostgreSQL backends
that became active summed to approximately 1.4% of one CPU on average, with zero reported wait.

This CPU sample did not overlap the two 01:58 timeout events. Report01's 92–98% idle snapshot was
also taken at a different time and access level. The two snapshots show no host-wide CPU
saturation, but they do not support a CPU improvement percentage.

At 07:47 JST a second five-second sample did overlap an optimized query that subsequently timed
out twice in the same backend. That PostgreSQL backend averaged 100.2% of one CPU with zero wait,
while the 24-vCPU host remained 90–91% idle with zero iowait and zero steal. No parallel worker was
present. The operational pattern is therefore a single search backend saturating one core until
the ten-second timeout while the VM as a whole retains CPU capacity; global idle CPU is not proof
that each search can finish.

Database cumulative counters were 23 temp files / 1,417,881,556 bytes and zero deadlocks. The
short observation did not establish a new temp-file delta attributable to search.

## Federation blocking

Patch 030 changes only Note query construction. Patch 010 remains the separate FederationChart
optimization; neither patch replaces Misskey's ActivityPub block enforcement.

The public read-only federation API returned ten instances for `blocked=true`, all with
`isBlocked=true`. A separate `federation/show-instance` request for one of those instances returned
HTTP 200 and `isBlocked=true`. No host name was recorded in this report.

This confirms current block-state exposure through two API paths. It does not exercise inbound
Inbox rejection, outbound delivery suppression, or a block/unblock transition. Those operations
would mutate Production and were intentionally not run. The isolated 2026.10.0 validation remains
the behavioral evidence: 28/28 API equivalence cases, zero mismatches, and equal
remove/add/restore transitions.

The local repository was clean and aligned with `origin/main` at
`b75a3bcd0ca5bc9571f5af95ae0126d4dada3321`. The annotated `v4.1.0` tag resolves to release commit
`172e219da1407a551219c0f69d83c51a54e1b518`; the tag is not GPG/SSH signed.

Current verification results:

- updater SHA-256: `4fc9af956091e5f5dbf4c156fabde6b56826aa12f6f8f969760a9110e18a2e39`;
- deterministic bundle SHA-256: `7b68d319e1b98938de80f56348839937809bfd9f4acc66fe2cb33eec99c11742`;

- the current controller lacks ShellCheck, so the complete `verify-release.sh` stopped at its
  explicit dependency gate. The release-time full verification remains recorded as PASS.

For each future official Misskey stable release:

1. Run `scripts/check-update-compatibility.sh` on a validation clone, never on the Production
   source worktree.
2. Require the stable tag and expected official commit; inventory migration-file changes.
3. Verify every manifest hash and apply 001/010/020/030 in order in an isolated worktree.
4. Treat a conflict as FAIL and `UPSTREAM_EQUIVALENT` as BLOCKED pending human review; do not use
   three-way or automatic conflict resolution. Remove a managed patch only after equivalent
   upstream behavior and regressions are proven.
5. In `--full` mode, provide an isolated `EXP003_DATABASE_URL` and fresh API equivalence/performance
   JSON. Require frozen install, exactly 25 managed tests with no skip, SPDX check, full build,
   28-or-more equivalence cases with zero mismatch, identical result identity, and zero test
   failures/timeouts.
6. Run `scripts/test-blocked-host-transition.mjs` in the isolated environment for
   unblock/block/unblock/block, reply/renote/subdomain checks, restoration, and optional service
   no-restart assertion.
7. Review `release-decision.json`, `release-decision.md`, migration inventory, logs, and checksums
   before preparing or publishing assets.
8. Use the runtime updater's preflight, backup, migration-ledger, source-state, health, idempotency,
   and rollback gates during a separately approved maintenance window.

## Residual issues and follow-up

1. 271 Misskey Note-search timeout events and 277 optimized PGroonga timeout statements were
   observed in the first 5 hours 53 minutes. 030 removes block-list expansion, but PGroonga
   selectivity, joins, visibility predicates, data distribution, and concurrent traffic still
   dominate affected queries.
2. `pg_stat_statements` spans from 2026-06-11 and includes only three completed post-030 calls in the
   matched row; it cannot provide a deployment-window comparison or count the 277 canceled queries.
3. Search request totals and Nginx request times were not readable, so timeout-rate normalization is
   unavailable.
4. A timed-out optimized search saturated one PostgreSQL backend/core in the second CPU sample,
   without host-wide saturation or parallel workers. Query-level follow-up is needed; adding VM
   CPUs alone does not address this single-backend path.
5. Production federation mutation tests remain intentionally prohibited; API state and isolated
   transition evidence are the available safety proof.
6. Install ShellCheck on the validation controller before the next release so the all-in-one local
   release verifier can run without relying on the recorded release-time result.
7. PostgreSQL log storage remains large and should be handled as a separate retention/rotation
   operation, not as part of the search fix.

Operational result: **030 SQL-shape improvement confirmed; overall Production search remediation
is PARTIAL because optimized searches still time out. The remaining evidence gap is a total-search
request denominator for a condition-matched timeout rate.**
